# The README standard

Distilled from the two repos that already read well, h3_dance_studio and
File Renamer. Every package here and every sibling repo meets it, so a
visitor entering through any door finds the same shape.

1. **The problem in two sentences.** What breaks without this, and what
   this does about it. Before any command, before any table.
2. **A quick start that runs.** The exact commands, in order, from a
   clean clone. If a step needs something installed, say which.
3. **A layout table.** File or directory, one line each, what it does.
   Not a tree dump.
4. **The exact test command.** `make test`, `python -m unittest`, whatever
   it is, verbatim, and where the fixtures live if tests need them.
5. **Honest limits.** What it does not do, what is unofficial, what is
   likeliest to break. Workable's widget API, the first Lighthouse run on a
   cold runner, the cloud sandbox that cannot reach ATS hosts.

The opening line carries the intersection when the repo is a proof asset:
a visitor should know within two sentences that the author judges frames
and ships software. Repo prose passes the repo profile of the voice lint,
no em dashes and no corporate vocabulary, and stays out of the letter
profile's way; documentation may use parentheses and lists.
